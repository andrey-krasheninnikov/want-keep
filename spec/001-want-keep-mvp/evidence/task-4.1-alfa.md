# Task-4.1: квалификация чтения Alfa

[English](task-4.1-alfa.en.md)

Дата: 2026-10-28. Задача: [#29](https://github.com/andrey-krasheninnikov/want-keep/issues/29).

## Объём и состояние

D-47 заменяет продуктовый объём D-37: текущие счета, дебетовые карты, операции и кэшбэк. По решению владельца накопительные счета, вклады и кредиты Alfa исключены. Общие финансовые функции и другие провайдеры сохраняются.

Завершён первый этап живого исследования структурированного read-контракта одного аккаунта. Коннектор, его нормализация, фоновый worker и suites `PROVIDER=alfa` / `AREA=alfa` ещё не реализованы. Ни финансовые записи, ни deployment admission не создавались. Исследование не является приёмкой AC-042 или AC-106.

## Наблюдавшиеся маршруты

Все маршруты ниже относятся к авторизованному кабинету `https://web.alfabank.ru`, а не к официальному Alfa API. Авторизацию и MFA выполнял владелец в отдельном Chrome с непостоянным контекстом. Личные браузерные профили не использовались.

| ID | Чтение | Подтверждённая форма и граница |
| --- | --- | --- |
| ALFA-E21 | `GET /api/v1/account/` | `accounts[]`: `number`, `type`, `openDate`, `properties`, отдельные `amount`, `total`, `holds`, `currentBalance`. Проверены чтение с `accountNumber`/`type` и чтение без фильтра. Значение `currentBalance` не объявляется собственными расходуемыми средствами без проверки семантики. |
| ALFA-E22 | `GET /api/v1/cards/masked-cards` | `cards[]`: `id`, `number`, `isCredit`, `isClosed`, `account.number`, lifecycle/status. Это источник карточного алиаса; отдельный баланс карты не создаётся. Маска не заменяет устойчивый card ID. |
| ALFA-E23 | `POST /api/v1/operations-history/operations` | Тело содержит `page`, `size`, `forced`, `filters`. Наблюдались пустой список фильтров и фильтр `type=accounts` со строковыми references. Ответ содержит `operations[]` и `pagesInfo.page/size`. Страницы 1 и 2 по 20 записей прочитаны отдельно. |
| ALFA-E24 | `GET /api/v1/operations-history/operations/{id}` | Детали используют ID из списка. Есть `id`, `operationId`, `dateTime`, `direction`, `amount`, `status`, `reference`, `fields`, `loyaltyDetails`. У прочитанного дохода `status=null`; он не превращается автоматически в `posted`. |
| ALFA-E25 | `GET /api/v1/loyalty/accounts` и `GET /api/v1/loyalty/accounts/{id}` | Список и сводка лояльности: баланс, прогноз, месячные начисления и общий кэшбэк. Сводка не устанавливает идентичность банковской выплаты и не создаёт доход сама по себе. |

В наблюдавшихся RUB-суммах источник передаёт `currency=RUR`, целочисленный `value` и `minorUnits=100`. Исходные числовые токены должны обрабатываться точно: исследовательское чтение формы JSON не доказывает точность будущей нормализации через Go/TypeScript или БД.

В истории наблюдались `HOLD`, `SUCCESS`, `FAILED`, а также отсутствующий или `null`-статус. Отсутствующее поле комиссии не равно нулю. Ответ счёта не содержит отдельного подтверждённого времени состояния баланса. `dateTime`, время ответа HTTP и время получения данных нельзя без обоснования подставлять вместо неизвестных финансовых дат.

## Проверка транспорта и ограничения чтения

Повторный запрос первой страницы вернул те же IDs в том же порядке. IDs первой страницы уникальны; прочитанная вторая страница не пересекалась с первой. Это наблюдения одного диапазона в одной сессии, а не доказательство полной истории, устойчивости offset-пагинации или lifecycle revisions.

Отдельно подтверждён повтор запроса истории с минимальным набором ранее наблюдавшихся заголовков: `accept`, `content-type`, `x-xsrf-token`, `x-security-request`, `device-app-id`, `ao-origin-application-id`, `zone-offset`. Значения остаются секретными и в документ не включаются. В этом прогоне для повторного чтения не требовалась передача антифрод-заголовков `x-gib-*`; это не обещание их общей необязательности.

Новый BrowserContext с временной копией cookies, отключёнными скриптами страницы и service workers успешно прочитал историю, список счетов и сводку кэшбэка. Его сетевой фильтр разрешал только проверенные GET и POST чтения истории. Метод PUT не разрешался. Сессии и банковские ответы оставались в памяти исследовательских процессов; они не сохранялись в репозитории, приложении или БД.

При просмотре полного кабинета наблюдался автоматический `PUT /api/v1/loyalty/accounts/{id}/last-seen-balance`. Он не входит в read allowlist. Автоматическая проверка отклонила дальнейший переход в полный раздел кэшбэка; сводка затем прочитана непосредственно через ранее наблюдавшиеся GET в контексте без скриптов страницы. Полноценная навигация кабинета не является готовым безопасным collector workflow.

У отдельного запроса через Playwright APIRequestContext выявлена ошибка проверки сертификата; точная причина цепочки доверия не установлена. Проверка TLS не отключалась. Успех браузерного чтения не доказывает готовность Node HTTP или маршрута с deployment-хоста.

## Незакрытые контрактные вопросы

- Подтвердить identity после reauthentication и для второго независимого аккаунта. Повторный вход владельца состоялся, но сравнение IDs между этими входами не проводилось.
- Проверить фильтр выбранной даты, конец истории, retention, пропуски и поведение страниц при новых или поздно изменённых операциях.
- Закрепить единицы и состав балансов, known/unknown комиссий, финансовые даты и правила для `status=null` без вымышленных фактов.
- Получить связь начисление → банковская выплата → изменение/отмена кэшбэка с устойчивыми IDs. Ожидаемое начисление не увеличивает деньги; подтверждённая выплата признаётся одним доходом по D-47.
- Реализовать и проверить нормализацию, vault enrollment, fences, worker, PostgreSQL-интеграцию и synthetic contract suites после закрытия относящихся к ним вопросов.
- Получить provider/host evidence для точного D-43 binding. Production и admission остаются без изменений.

Второй независимый аккаунт будет доступен позже. До обязательных доказательств issue остаётся открытой. Статус SDD: **Ready for development**; приёмка коннектора и эксплуатационная готовность не подтверждены.
