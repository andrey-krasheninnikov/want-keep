# Task-4.2 — нативный Raiffeisen RBO/CAMT

Реализован backend для расчётного счёта ИП: подключение, личная OAuth-церемония внешнего владельца, encrypted token vault, ротация refresh, чтение счетов и дневных выписок через native Go gateway. Работа ограничена allowlist legacy RBO: список счетов, создание camt.052/camt.053 отчёта, его статус/файл и OAuth. Платёжные маршруты и браузерный collector здесь не используются.

Подключение использует семейную область и общий command recovery. Смена поколения отзывает секреты и задания; партнёр может запросить reauth, но не получить OAuth URL или завершить чужой callback. Одноразовый state связан с owner/session/connection/revision/generation и действует пять минут. Попытка сохраняется до обмена code; потерянный ответ не запускает повторный обмен. Завершённый callback читается повторно. Signed ID token проверяется по заранее подтверждённым issuer/JWKS, audience, nonce, subject, expiry, допустимому RS256 и access hash при его наличии. Неполная конфигурация запрещает Code Flow. Legacy endpoints не заменяются новой `/oauth2` схемой.

Refresh и запрос отчёта сохраняют claim до внешнего IO. Неизвестный результат не повторяется автоматически. Неразрешённый отчёт запрещает новые report requests в текущем поколении; операторское уточнение или новая авторизация нужны до продолжения. Refresh старой revision сериализуется; новые токены сохраняются зашифрованно с новой revision и неизменяемым AAD. Provider/host admission, generation и lease проверяются перед IO и внутри общего CommitPage. Revoke после чтения сохраняет evidence в quarantine без journal effect.

CAMT поддерживает 1:N entry/details, точные суммы, RUR/RUB и раздельные Account UUID/accountKeys. Optional references регистрируются атомарно. Fingerprint v1 не включает amount/time/report ID и не зависит от появления optional alias. Пустой remittance и `NOTPROVIDED` не подтверждают достаточность идентичности. Противоречащие сильные references одного вида дают неоднозначность даже при одинаковом семантическом hash; отсутствие alias или появление нового вида само по себе не является конфликтом. Семантический hash исключает raw digest новой выписки; raw bytes сохраняются как evidence. Изменение проводится как correction только при сильной ранее сохранённой reference и более новом sourceAsOf. Совпадение parties/remittance без такого доказательства остаётся source_ambiguous. CLBD сохраняет owned observation; available/locked/debt/credit limit неизвестны без подтверждённого mapping. OPBD не создаёт доход или историческое открытие. Неоднозначный FCHG не назначает комиссию автоматически.

## Проверки и live-доказательство

- `make test-contract PROVIDER=raiffeisen`: parser, 1:N, precision, optional aliases, пустой remittance/placeholder, неверный account/namespace/amount/XML directive, allowlist, неизвестная token rotation, OIDC signature/nonce/subject/expiry, время выдачи токена после начала запроса и PKCE; отзыв permit между status/file запрещает второй запрос.
- `make test-raiffeisen-race`: PostgreSQL 17.11 с непривилегированной ролью, HTTP create/replay, owner callback/readback, конкурирующие claims, reauth generation, worker ingestion/replay, correction/collision при равном и изменённом payload, отзыв admission между status/file и commit-time quarantine.
- `make check` прошёл: форматирование, lint, типы, unit-тесты, сборка, RU/EN-каталог и воспроизводимость Go/TypeScript. Общая ingestion suite также прошла; итог доставки подтверждается отдельно по опубликованному кандидату.
- 2026-10-03: разрешённый нативный read-only conformance успешно обновил токены, получил один существующий счёт и новую camt.053 выписку за 2026-08-01–2026-08-31. Нормализованы семь details без parser gaps. Ответы сохранены приватно вне Git; команды не создали записи журнала или admission.
- Исправленный parser повторно проверен на уже сохранённом приватном отчёте без банковского IO: семь details, ноль parser gaps.

Это не доказательство полной истории, корректности всех proprietary fee codes, live camt.052, браузерного Code Flow, повторного банковского входа или двух реальных аккаунтов. Исходная попытка прочитать старый report не прошла; успешное доказательство относится к новому отчёту. Production, VPS и допуск подключения не менялись. ## Настройка до deployment

API и worker читают `WANT_KEEP_JOB_BINDINGS_FILE` и `WANT_KEEP_CONNECTION_KEYRING`. Для Code Flow/refresh нужны `WANT_KEEP_RAIF_CLIENT_ID_FILE`, приватный `WANT_KEEP_RAIF_CLIENT_SECRET_FILE`, подтверждённый `WANT_KEEP_RAIF_ISSUER` и локальный trusted `WANT_KEEP_RAIF_JWKS_FILE`. Redirect URI фиксирован: `https://want-keep.tech/api/v1/connections/raiffeisen/callback`. Отсутствующая конфигурация безопасно закрывает авторизацию. Binding file лишь описывает сборку, но не выдаёт допуск. Provider и host checks записываются отдельно для точного D-43 binding/admissionRevision.

`backend/cmd/raiffeisen-conformance` работает только с явно переданным приватным каталогом вне Git: `tokens.json`, `refresh-state.json`, отдельный secret file. Directory — 0700, файлы — 0600. `-refresh` явно разрешает один обмен; durable marker остаётся pending при неизвестном исходе. `-from/-to` создаёт один исторический отчёт и сохраняет его ID до повторного чтения. Секреты, raw XML и персональные реквизиты не помещаются в публичные fixtures, командные результаты или журналы. Этот CLI не является способом установки токенов в production vault.
